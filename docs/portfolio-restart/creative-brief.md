# Portfolio restart: creative brief and implementation plan

Date: November 11, 2026. Status: independent Codex proposal; not user-approved art direction.

## The argument

Quintin connects software to things people can use, play with, and hold. The portfolio should make that range immediately tangible, then make the engineering evidence easy to inspect. Primary audience: software engineering hiring teams; secondary audience: collaborators and people who enjoy the projects. Primary action: inspect a real project. Résumé and contact never require a game or an introduction.

The distinctive material is already here: the hockey-themed physical pinball machine; a fabricated two-player arcade; One Piece card collecting; a local ship-themed AI workspace; Unity training systems; fabrication for Code Lavender; a Computer Engineering degree; New York/Long Island availability; production internship experience; and explicit limitations on experimental work. Preserve all nine project records, original demos, case study, links, résumé, experience, education and contact. Source data and original homepage remain authoritative and unchanged.

## What went wrong before

The folded paper and pixel buildings used incompatible visual languages. Repeated buildings became project cards in costume. Expanding to nine destinations happened before a single scene established a convincing art standard. Functional testing did not establish visual acceptance. Those implementations are rejected, not a foundation to reuse.

## Three directions

### A — The builder's studio (recommended for this comparison)

One art-directed, tactile workshop illustration introduces the relationship between hardware, software and play. Warm cream and butter yellow, dark blue ink, a deliberate vermilion accent. Large readable sans-serif typography; miniature craft and nautical/game objects carry personality. Original project photos and interfaces take over when evidence begins. Ordinary vertical reading and dedicated project pages keep hiring information direct. A project-type selector lets visitors explore the work rather than learn game controls.

Strength: specific to the actual pinball/arcade/software mix, warm and memorable. Risk: generic generated desk art would dilute it. Hero art must have coherent materials, perspective and lighting, and must be labeled as an illustration rather than evidence. This is an illustrated site, not a claimed interactive 3D environment.

### B — The adventure journal

One richly illustrated coastal workshop world, in gouache/ink throughout, with editorial project chapters. Ivory, navy, sea green and restrained coral. Serif headlines with neutral body text. Nautical exploration carries the One Piece influence without requiring copied characters. Mobile uses cropped chapter illustrations, not a shrunken entire map.

Strength: strongest sense of exploration. Risk: high illustration burden and greater temptation to conceal information. Needs a scene bible, a complete art set, mobile crops and transitions before implementation. No folded-map intro or placeholder island geometry.

### C — Playful engineering

An editorial portfolio with oversized typography, bold cobalt/cream/red fields, large real project imagery, and a very small pixel vocabulary. Pinball and TCG Shelf are the cover subjects. Mobile follows the same photographic/typographic hierarchy. Motion is one crisp image-to-project transition, not travel through a world.

Strength: clearest evidence, fewest new assets, easiest to keep coherent. Risk: could become a generic designer portfolio unless real hardware and game details dominate. No decorative dashboard boxes or arbitrary faux technical annotations.

## Implementation stages and acceptance

1. Freeze this brief and a shared comparison prompt. Record provider/tool differences; a blocked runtime receives no design-quality score.
2. Produce a direction board, desktop composition and narrow composition. Current implementation is a reviewable proposal, not acceptance of A.
3. Build one complete route at /studio: introduction → Pinball → full evidence/demo → back. Keep original homepage unchanged. Give other projects their complete existing records without pretending their art direction is finalized.
4. Inspect desktop and phone screenshots. Reject clipped titles, conflicting illustration styles, weak project evidence, text over noisy art, or identity that depends entirely on franchise logos.
5. Check keyboard navigation, reduced motion, native links/history, demos, complete project records, build/types and route isolation. Passing these checks does not approve the visual direction.
6. User selects or revises the direction. Only then expand bespoke art, richer motion and the remaining content presentation. No merge, production deployment or replacement of the live homepage.

## Proposed visual rules for A

Cream #f5f0e6, ink #172e38, yellow #efc44f, red #b93e2d. Body 17–19px, line height 1.55; expressive headings with enough room to wrap on mobile. One family does ordinary reading; existing pixel type appears only as a small game-related accent. Illustration occupies one dominant area. Real screenshots use their actual proportions. Motion is optional and brief; never blocks content. Ordinary focus rings, semantic headings, 44px controls and a direct original-portfolio link.

## Comparison rubric (unscored until output exists)

Score identity, composition, typography, art consistency and project specificity separately from usability, completeness and feasibility. Record actual model/provider, available tools, elapsed time, generated assets, interventions, failures and checks. Codex has browser/file/image-generation tools; the observed Sunny local profile has advice-only capabilities. This is a workflow comparison, not a controlled model-only benchmark. Neither working code nor a good-looking concept image alone wins.
